00 The three commands

“Start everything” is not one process. It is three, because the live portal and the fleet cannot both have the machine — and one of them is limited by something no code can fix.

1. API + dashboard
   python scripts\run_server.py          # FastAPI on :8000, metrics on :9090
   cd frontend && npm run dev            # Vite dev server, log in as admin

2. The fleet — 28 cameras, full pipeline, ~9.7 fps each
   .\start_fleet_demo.ps1                # 8 worker processes, recorded footage

3. One genuinely live camera
   .\start_cam09_live_demo.ps1           # corp8 portal, ~15 min window, start it last

Order matters. The fleet takes about two minutes to load eight copies of the models and reach rate. The live camera spends a metered quota from the moment it connects, so it is started immediately before anyone is watching.

Limit — 30 live cameras at 10 fps is impossible from this portal

The corp8 account is metered on wall-clock watching, account-wide. Fetching all 30 cameras at real-time pace, every one of them was refused with HTTP 403 within a ten-second spread at t+15 minutes — a per-camera limit would have staggered them. A separate HTTP 429 throttle held the account to 626 segments in 900 s ≈ 7 seconds of video per wall second. Thirty real-time cameras need thirty. That is roughly seven cameras, for fifteen minutes, after which the cooldown exceeded 15 minutes and had not lifted at 40. This is a supply limit at the source; no architecture change reaches past it. Genuine 30-camera live needs the police RTSP/NVR feed.

Limit — plates are readable on one camera

Across this fleet plate characters are about 7 px tall; that is below what any recogniser can read. ANPR is therefore enabled on CAM_09 only, whose geometry actually resolves plates. The shipped recogniser scores 59.0% exact / 93.1% character accuracy on 83 held-out real vehicles, rising to 80.4% exact over 61.4% coverage at plate width ≥ 80 px with confidence ≥ 0.85. Quoting a single fleet-wide ANPR accuracy would be dishonest.

Limit — camera “health” is not per-camera

All 30 registry rows share one heartbeat timestamp, so a green ONLINE badge on the fleet map means the system is up, not that that camera is. The honest liveness evidence is the per-camera row in Fleet Operations — frames processed, fps, last frame age — which comes from the worker that owns the camera.

Real — the compute was never the wall

Fed from recorded footage, which carries no quota, 28 cameras run the complete pipeline at 9.69 fps each (261.5 frames per second completing detection, tracking and appearance) on this one desktop. The fleet target was a supply problem, not a compute problem.

02 Stream connection

Every camera is an independent object with its own thread, its own reconnect state and its own failure counter. Nothing about camera 12 can reach camera 13.

S1aSource resolution & identitySQLAlchemy · Camera registry
Input
The cameras table — camera_id (the stable key, e.g. CAM_09), stream URL, zone, district, lat/lon, is_deleted, test-camera flag.
Processing
fleet_supervisor.discover_cameras() reads the registry, excludes deleted and test rows (fleet_census.is_test_camera), sorts for a stable order, and assigns cameras to workers round-robin so the same camera lands on the same worker on every restart.
Output
A plan: worker → camera list, written to output/fleet/supervisor.json.
Failure
A camera missing from the registry simply is not started. A camera present but unassigned appears in Fleet Operations as unassigned rather than vanishing from the totals — the count of registered cameras and the count being processed are reported separately, so a gap is visible.
S1bOpening the streamOpenCV / FFmpeg · HLS, RTSP, ONVIF, file
Input
The camera's URL.
Processing
_detect_source_type() classifies the URL into rtsp, http, onvif, file or clips and opens it with cv2.VideoCapture. This fleet's cameras are AES-128 encrypted HLS behind a login, not raw RTSP: credentials live only in the git-ignored config/corp8_credentials.json, a session is minted once and its cookies reused, and any URL that reaches a log goes through _mask_url() so a password can never be printed.
Technology
For the one live camera a dedicated relay (cam09_live_relay.py) prefetches HLS segments in parallel, decrypts AES-CBC locally and serves plain MPEG-TS on 127.0.0.1:8091. That is what lifts the live rate from the portal's ~1.5 fps of straight streaming to 12.5 fps; the wall is request latency, not bandwidth.
Output
An open capture handle, plus _stream_width/_stream_height for the telemetry.
Performance
Measured bandwidth for all 30 cameras at real-time pace: ~2.0 MB/s. Bandwidth has never been the constraint.
Failure
A failed first connect increments that camera's own failure counter. With SENTINEL_STRICT_LIVE=0 the camera falls back to its recorded clips and is flagged _in_failover, which propagates to the on-screen banner so a failover is never shown as live. With strict live on, it retries and stays dark rather than substituting footage.
S1cReconnection, timeouts, quotaper-thread backoff
Processing
Each loop checks cap.isOpened(); a closed network source enters _handle_network_reconnect() — backoff, re-open, and a reconnect counter that the dashboard shows per camera. TCP connect timeouts are deliberately short so an unreachable host costs that camera a moment, not the fleet.
Technology
The portal's two refusals are told apart by response body, not status alone: a 403 whose text says watch time limit reached is a quota, and logging in again lifts nothing. The relay therefore sits out the cooldown with no logins (one playlist probe every 150 s). Six workers each sleeping and re-logging in every 20 s was what perpetuated an earlier lockout.
Output
During a cooldown the dashboard shows the last live frame dimmed, stamped LIVE PAUSED with the reason and the time of the last real frame — not a frozen picture pretending to be current.

03 Ingestion and decode

S1dFrame acquisitionCameraReaderThread · one per camera
Input
An open capture.
Processing
Each thread decodes, stamps the frame with a capture timestamp and a FrameOrigin (clip path and frame number, so evidence can later be cut from the exact moment the detector was looking at), then offers it to the worker's shared bounded queue with put_nowait.
Rate control
Two mechanisms. Network sources sleep to hold target_fps (SENTINEL_READER_FPS). Recorded sources additionally decimate by stride = clip_fps / target_fps, so a 25 fps clip yields 10 fps without decoding frames it will throw away.
Resolution
Frames are kept at source resolution end to end. Only the detector's own input is scaled — plate crops, ANPR, speed and the training vault all cut from the original frame, never from a resized copy, which is why detector-side resolution knobs cannot damage recognition.
Isolation
This is the answer to “how does one slow camera not block the others”: a slow camera's thread blocks on its own read(); the queue is bounded, so a fast camera cannot flood it either. When the queue is full put_nowait raises and the frame is counted as dropped and discarded rather than waited on.
Performance
The drop counter is the fleet's real backpressure signal. It read 26.2% before this week's fixes and 18.1% after, at 10 fps asked of 28 cameras.
Read this before quoting any fps number

The per-camera fps_now on the dashboard is derived from frames_queued, which counts every decoded frame — and frames_dropped counts only those that could not enter the inference queue. Decode read 9.86 fps per camera while the pipeline was actually completing 7.76. Any claim about the fleet must use health.total_frames_processed as a rate. Every figure in this document does.

04 Process architecture

One supervisor process, eight worker processes, and inside each worker four kinds of thread. Python's GIL is the reason the outer layer is processes and not threads.

UnitCountRunsWhy this shape
fleet_supervisor1Plan, spawn, watchdog, restartOwns nothing on the GPU; if it dies the workers keep running.
Worker process8Models + its share of camerasSeparate interpreters, so eight inference loops run truly in parallel. Measured: 8 workers beat 6 by 0.8 fps per camera.
Reader threadper cameraDecode + rate controlDecoding releases the GIL, so threads are the right tool inside a worker.
Inference thread1 per workerDetect → embed → track → persistSingle consumer, so the GPU sees one ordered stream of batches per process.
Publisher thread1 per workerJPEG encode + atomic writeAdded this week. Encoding was 11.8 ms of every frame, on the inference thread.
Vault writer thread1 per workerTraining-crop writesKeeps a single SQLite writer and keeps commits off the inference path.

GPU allocation

Each worker calls torch.cuda.set_per_process_memory_fraction() with its share (SENTINEL_WORKER_GPU_FRACTION, 0.1 each for eight). This exists because five workers plus a demo pipeline once reached 11,914 MB of a 12,282 MB card and the two processes froze each other for ~1.5 s at a time. A second cap, SENTINEL_INFER_BATCH, bounds how many frames are drained into one batch, because the CUDA allocator holds the peak batch's memory afterwards — capping it took one pipeline from 3.2 GB to 887 MB.

How real-time is held

It is held by admission, not by hope: readers produce at a fixed rate, the queue is bounded, and anything that cannot be processed is dropped and counted rather than queued into a growing backlog. Latency therefore stays flat while throughput degrades visibly — the opposite of a system that looks fine until it is minutes behind.

05 The nine stages

One pipeline, not several. ANPR is not a separate service — it is called inline from the frame loop. The strip below is the whole path; the hot stages are the ones that cost GPU time.

1 Ingestion2 Vehicle detection3 Tracking4 ANPR5 Identity fusion6 Trajectory + speed7 Traffic analytics8 Alerts9 Persistence + UI
Stage 2Vehicle detectionYOLOv8 · Ultralytics · CUDA fp16
Input
Up to SENTINEL_INFER_BATCH frames drained from the queue across all of that worker's cameras at once.
Processing
Every frame is letterboxed onto one common canvas so the batch forms a single tensor — aspect ratio preserved, grey padding, and the pad offset kept so boxes map back to each camera's own pixel coordinates. Then one predict() for the whole batch, restricted to COCO vehicle classes.
Model
YOLOv8s fleet-wide; yolov8m on CAM_09, where the overhead sun-glared view made v8s miss a plain white SUV even at confidence 0.10 (+15% vehicles for 29 vs 14 ms).
Output
Per frame: boxes, class ids, confidences — plus a flat list of vehicle crops for the next stage.
Performance
2.80 ms/frame in isolation at batch 16; 16.9 ms inside the running fleet, the difference being queuing on a GPU at 91%. A double resize was removed this week (the canvas is now capped at imgsz), which alone took detect from 14.0 to 11.5 ms.
Failure
A failed batch is logged with the frame count and the whole batch is skipped — one bad frame cannot stop the loop.
Stage 3Appearance embeddingOSNet-IBN x1.0 · torchreid
Input
Every vehicle crop in the batch, pooled across cameras.
Processing
One extract_batch() for the entire cycle, so the model is called once per batch rather than once per camera. Serves two consumers: the tracker's appearance association, and the per-track running mean that becomes the vehicle's stored signature.
Model
OSNet-IBN fine-tuned on Market-1501, checkpoint model.pth.tar-250.
Performance
~1.1–1.3 ms per crop at fleet batch sizes. SENTINEL_EMBED_EVERY=5 embeds each track about twice a second instead of every frame; measured worth +0.4 fps per camera and a large cut in drops once the GPU became the constraint.
Failure
An embedding failure is caught and logged: association falls back to motion only. Degrades the result; does not stop the cameras.
Stage 6Speed and trajectoryhomography · Theil–Sen · OSRM
Input
The bottom-centre of each box — the contact point with the road plane — per tracked frame.
Processing
Where the camera is calibrated, the point is mapped to metres through the homography and the track's speed is fitted with Theil–Sen (robust to the outliers that box jitter produces). Points the geometry cannot actually measure are rejected before entering the buffer, using a bound derived from the homography itself — without it, one bus track produced an 84,445 m path.
Output
km/h per track; map-matched corridors via OSRM with an offline cache.
Honesty
CAM_09 is the only camera with a validated scale (7.6 m lane-dash pitch, agreeing to 1% across 57 car widths). Earlier CAM_08/CAM_11 calibrations were measured 3× wrong and deactivated. Uncalibrated cameras report no speed rather than a plausible-looking default — a literal 42.0 km/h prior once appeared on 29 cameras labelled “Live Speed”, which is exactly the failure this rule prevents.

06 Tracking

Stage 3BoT-SORT, one tracker per cameraKalman + IoU + appearance + GMC
Input
That camera's detections for one frame, its appearance features, and the frame itself.
Processing
Each camera owns an independent BoTSORTTracker keyed by cam_id, constructed with that camera's effective frame rate so the motion model's time step is right. Association combines a Kalman motion prediction, IoU, and the OSNet features. Track ids are camera-local by design.
Camera motion
Global motion compensation (sparse optical flow, downscale 8) separates a pan from vehicle motion — without it a panning camera reads as every vehicle moving. It is gated: a cheap motion test runs each frame and full GMC only when the camera actually moved (1 run in 55 on a fixed camera).
Duplicates
The detector often returns two boxes for one motorcycle. A same-class overlap test (IoU ≥ 0.3, or 60% containment) suppresses the second before it is drawn or counted.
Occlusion
A track that disappears is kept alive for a bounded number of frames and re-associated on reappearance by motion plus appearance. Beyond that it is flushed and persisted.
Display
BoT-SORT returns only confirmed tracks, and on a panning handheld camera a clearly visible motorcycle went unboxed on 45% of frames. High-confidence unconfirmed detections are therefore drawn too, with the class and no id — an id appears only when the tracker has earned one.
Performance
1.2–3.4 ms per frame. A known limitation: id switches can split one real vehicle into two or three vehicle_track rows, so a raw row count overstates vehicles.

07 Cross-camera identity

The question “is the vehicle on CAM_05 the one that later appears on CAM_20?” is answered by appearance first, plate second, and physics as a veto.

Stage 5Identity fusionOSNet mean vector + plate key + transit prior
Input
Each finished track's mean appearance vector, its camera, its time window, and any plate read.
Processing
A committed plate is an exact key and wins outright. Without one, the track's mean vector is matched against the gallery by cosine similarity, then filtered by whether the journey is physically possible — camera locations and timestamps bound how fast the vehicle could have travelled. Corridors are map-matched with OSRM so a “journey” follows real roads rather than a straight line.
Output
A stable GV_xxxxxx identity shown on every camera's tile, plus journey_events rows forming the trajectory.
Guarding against false matches
Three lessons, each learned from a wrong result: (1) the similarity threshold must be calibrated in-domain — calibrating on other cameras' crops silently grouped vehicles by colour; use same-frame pairs as impostors. (2) Budget false links per run, not per comparison. (3) A transit prior is required, because parked vehicles otherwise win every match by sheer number of appearances.
Evidence
Proven on a controlled set: one motorcycle across four cameras against a ~500-vehicle gallery, leave-one-out Rank-1 4/4; and against a 503-vehicle gallery, Rank-1 100%, mAP 95.8%. That is a clean result on a known subject — not a claim of fleet-wide accuracy, which has no ground truth here.
Provenance
914 of the journey rows in the database were generated, not observed, and are excluded by a provenance predicate. Events-per-plate is the sanity check (~1.12 for seeded rows against ~8.19 for live ones).

08 ANPR — seven sub-stages

Called inline from the frame loop for cameras on the ANPR list. Every cost guard below already exists in process_vehicle_track; a locked plate returns immediately with no OCR at all.

StepWhat it doesModel / technique
4.1Lighting normalisation before anything elseAdaptiveNightEnhancer, four tiers chosen from the crop's own statistics
4.2Tight plate box inside the vehicle cropYOLOv8 plate detector (plate_v3_ft, small variant plate_v4_small), retrained 2026-09-02 — finds 2.6× more plates on live footage
4.3Lighting-aware crop preprocessingPlatePreprocessorV2; geometric rectification present but default OFF — median plate tilt here is 0.00°, so there is nothing to straighten
4.4Quality gate: sharpness, contrast, minimum widthPlateFrameSelector — picks the sharpest N views of a track instead of OCR-ing every frame
4.5RecognitionEnsembleOCR: three-model CRNN primary with an EasyOCR fallback
4.6Grammar and state resolutiondecode_plate() v2, all-India plate grammar
4.7Multi-frame agreementTemporalPlateVoter — confidence-weighted vote across a track's reads, then the plate locks

Handling hard plates

Low light is 4.1's job; angle is 4.3's (and measurably unnecessary here); blur and small size are rejected by 4.4 rather than guessed at — a refusal to read is a correct output. Partial occlusion is where the system deliberately does less: double-line slicing is off, because the CRNN was trained on complete single-line plates and hallucinates confidently on half of one (GJ03 → GJ8088). Fixing that needs retraining on strips, not a better gate.

Inconsistent reads

Resolved by 4.7's weighted vote, then by the lock — once a track has a committed plate, later frames cost nothing. Cross-track conflicts are handled at stage 5, where the plate is an identity key, and by the clone-plate detector at stage 8, which checks whether one plate's sightings are physically possible (10/10 on known-answer tests, 0 false alerts across 727 real events).

Measured dead ends — do not re-attempt these

Seven approaches to raising plate accuracy have been measured and failed on this footage: logit fusion (−23.6 points), self-training on the unlabelled pool (0 of 300 accepted), plate-scale-from-height, and blending the synthetic corpus into the real one among them. The ceiling is optical, not algorithmic: the lever that remains is more real labelled plates.

09 Event generation

Stage 8From detections to things worth telling someonewatchlist fuzzy match · clone physics
Input
A committed plate, a finished track, or a cross-camera association.
Processing
Three generators. Watchlist: a committed read is fuzzy-matched against the wanted list — 86.5% recall at 0% false alarms, which is the number that matters operationally, not the raw transcription rate. Clone plate: one plate seen in two places too far apart too soon. Journey: a sighting joined to a trajectory.
Output
Rows in alerts and journey_events, each carrying camera id, vehicle/track, plate, timestamp, the camera's coordinates, and a snapshot reference — plus a danger score on a 0–10 scale.
Provenance
Every staged or generated row carries is_simulated, and the serializer exposes it. A demo case is staged and marked; the flag was once hidden by the serializer, which is precisely how a simulated row can come to look real.
Delivery
Pushed to the dashboard over the WebSocket; the alert feed also polls as a backstop so a dropped socket cannot silently stop alerts.

10 Database and write discipline

SQLite in WAL mode (DATABASE_URL switches the whole stack to PostgreSQL), and the important design decision is when rows are written, not what is in them.

TableWritten whenHolds
vehicle_trackOn track flush — once per vehicle, not per frameCamera, class, first/last seen, speed km/h, plate, box history
track_appearanceAfter the track transaction commitsThe track's mean OSNet vector, hash, expiry (180 days)
journey_eventsOn cross-camera associationSighting chain, corridor, provenance flag
alertsOn watchlist / clone matchReason, score, evidence refs, is_simulated
camerasRegistry, rarelyIdentity, location, zone, calibration link
Vault cropsWriter thread, sampledBorderline-confidence crops + embedding, for retraining

Avoiding writes that slow the pipeline: nothing is written per frame. Track points accumulate in memory and are persisted once at flush; appearance vectors are a running sum, not a row per frame; the vault has its own writer thread and a bounded queue that drops and counts when it falls behind; and the fleet-wide analytics rollup runs on one worker only (SENTINEL_ROLLUPS) — every worker was running the same whole-database rollup, costing 230 ms per frame on one of them.

Two persistence bugs worth remembering

A variable used before assignment rolled back the transaction on every successful plate read — CAM_09 went from 0 to 36 reads when it was fixed. And a flat homography array never reshaped left speed_kmh NULL on 100% of 227,636 tracks, hidden by a bare except. Both argue the same thing: no silent excepts on the persistence path.

Historical search runs over these tables: plate search, vehicle journey search (91.1% precision / 85.0% recall on the stored artifact), time and camera filters, and appearance search against the embedding column.

Video reaches the browser as MJPEG multipart, one HTTP connection per visible tile. Two consequences shaped the UI: browsers cap connections per host at six, and a detached <img> keeps its stream open — which took Firefox to 20 open connections and blanked the views. Tiles now clear src on unmount, the modal streams from 127.0.0.1 to use a second connection pool, all tiles pause while a modal is open, and the server evicts more than two streams per client per camera.

Handling 30 cameras' update rate: detections are not broadcast per frame to everyone. Video is pulled by whoever is looking, at the rate the publisher produces; aggregates are polled at a fixed rate independent of camera count; and only events — which are rare — are pushed. So dashboard load scales with viewers, not with fleet frame rate.

Known operational gotcha

On Windows, terminating the supervisor does not kill its worker processes. Leftovers keep writing the same heartbeat files, so the dashboard shows two generations of the fleet at once — it produced readings of “3342 fps” and “detect 572 ms” in testing. start_fleet_demo.ps1 kills every run_pipeline before starting.

imgsz stays at 640. Dropping to 480 bought 0.38 fps at six workers and costs detections on distant vehicles — the wrong trade for a traffic-analytics system. The GPU at 91% is now the ceiling: the last 0.3 fps needs a lighter detector and its recall, or a second card.

What runs once, what runs per camera

  • Once globally: the supervisor, the analytics rollup, the API, the database.
  • Once per worker: model weights, the inference loop, the publisher, the vault writer, the GPU allocation.
  • Once per camera: the reader thread, the tracker, the track buffers, the environment classifier cache, the published frame.

Adding cameras

Insert a row in cameras and restart the supervisor. Nothing in the pipeline is keyed to a fixed camera list, and the per-camera state above is created on demand — camera-specific behaviour is expressed as environment lists (SENTINEL_ANPR_CAMERAS, SENTINEL_ALIGN_OVERLAY_CAMERAS, SENTINEL_GLOBALID_CAMERAS) rather than branches in code. Beyond this machine, the horizontal unit is the worker process: it already runs with its own GPU share, its own cameras and its own heartbeat file, so moving workers to a second host needs the heartbeat files replaced by a shared store, not a redesign.

corp8 HLS portal		Police RTSP / NVR (ONVIF), already supported by the readerThe single highest-value change. Measured: the account gives ~7 camera-seconds of video per second and cuts off at 15 minutes. Every other limit in this document is smaller than this one.
Decode
CPU via OpenCV		NVDEC hardware decode, scaled on the GPUDecode is the largest CPU cost left and lands frames already in GPU memory, removing a host→device copy per frame.
Detector runtime
PyTorch fp16		TensorRT — now, not beforeEarlier it would have been wasted: the bottleneck was a JPEG encode on the inference thread. With the GPU at 91% it is finally the binding constraint. Note ONNX-CUDA gave no gain over PyTorch (6.7 vs 6.1 ms), which is itself the evidence that the cost was Python, not GEMMs. TensorRT libraries are not installed (nvinfer_10.dll missing).
Frame handoff to UI
JPEG files + MJPEG		Shared memory in-process; WebRTC to the browserWriting and re-reading a JPEG per camera per frame is a filesystem round trip for data that never leaves the machine; WebRTC also removes the six-connection browser cap that already blanked the grid once.
Database
SQLite WAL		PostgreSQL + pgvector (DATABASE_URL already switches it; the models already branch on dialect)Not needed at today's write rate — writes are per track, not per frame — but SQLite has one writer, and appearance search wants a real vector index rather than a scan.
Worker coordination
Heartbeat JSON files		Redis or NATSFiles are honest and dependency-free on one host and should stay until there is a second host. They also cannot express "this worker is gone" — which is exactly the Windows leftover-worker bug above.
Language / framework
Python, FastAPI, React		Keep.The measured costs were a double image resize, a JPEG encode on the wrong thread, and GPU contention — none of which a different language fixes. Rewriting would spend the month before the hackathon re-earning ground already held.
